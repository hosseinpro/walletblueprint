Security architecture principles for hardware wallets

A hardware wallet is not a safe. It is a small machine that must tell you the truth about what you are signing, and keep one secret while doing it. Five properties decide whether it can. Everything else — coin support, app polish, price — is downstream.

The scores in the comparison table are not a review average. Each is a reading of one part of the device's architecture, taken from public datasheets, firmware source, certification reports and our own bench work. Where a claim cannot be verified, it is scored as if it were absent.

01 — SECURE ELEMENT

The secret should live somewhere that cannot be read.

A general-purpose microcontroller stores your seed in flash that a skilled attacker with physical access can often extract — through voltage glitching, decapping, or a debug interface someone forgot to fuse off. A secure element is purpose-built against exactly that: hardened memory, active shielding, glitch and fault detection, and no path that returns key material to the outside world.

We score three things. Whether the seed is generated and used inside the element rather than merely encrypted by it. Whether the element is independently certified at a meaningful level. And whether the firmware running on it can be reasoned about — a closed element with an open host MCU is a different risk from a fully closed stack.

Full marks require: key material never leaves the element, certified silicon, and a documented attack surface between element and host.

02 — TRUSTED SCREEN

What you see must be what you sign.

Assume the computer is hostile. The only defence left is a display the host cannot influence: driven directly by the signing firmware, over a bus nothing else shares, rendering the address and amount the device is actually about to authorise. If a companion app can put pixels on that screen, the screen proves nothing.

Resolution matters less than people think, and legibility more. A screen that truncates a destination address to eight characters invites address-substitution malware to brute-force a lookalike. A screen that cannot render the full contract call is, for smart-contract use, close to blind signing.

03 — TRUSTED INPUT

Consent has to be physical.

Confirmation is only meaningful if it cannot be produced by software. That means buttons or a touch controller wired to the secure domain, a signing step that cannot be batched away by an earlier approval, and a PIN entered on the device rather than typed into a host that may be logging it.

We also penalise interfaces that make the safe path tedious. Devices that hide address verification three menus deep, or default to a “trust this session” mode, lose points: an input path humans route around is not a control.

04 — ENTROPY

A predictable seed is no seed at all.

Every key in the device descends from one number generated once, usually in the first minute of the device's life. If that number is weak, every other control is decoration. We look for a hardware noise source rather than a software PRNG, health tests that run at generation time and fail loudly, and a documented mixing function — ideally one that lets the user contribute their own entropy, dice rolls included, without having to trust the device alone.

Verifiability is the differentiator here. Several devices generate perfectly good entropy that a user has no way to audit. That earns a solid score, not a top one.

05 — OPEN SOURCE

A claim you cannot check is a claim you are trusting.

Open source is not a security property by itself — plenty of open firmware is unreviewed, and a closed secure-element applet can still be excellent. What openness buys is the ability to verify the other four. If the signing firmware is published and the build is reproducible, the binary on your device can be shown to match the code people have read.

We score the proportion of the stack you can read and rebuild — signing firmware first, then bootloader, then host application — and we require reproducible builds plus a signature scheme that lets you confirm what is actually installed. Vendors are scored down where “open source” covers only the desktop app while the firmware that touches your seed stays closed.

Full marks require: published signing firmware and bootloader, reproducible builds, and a way for the user to attest the running image.

SCORING

9 – 10
Property implemented and independently verifiable
7 – 8
Sound design, one documented gap or unverifiable claim
4 – 6
Partial coverage, or mitigations that depend on the host
0 – 3
Property absent, or claimed with no way to check

The composite is an unweighted mean of the five, rounded to one decimal. We publish it because people want one number, and we refuse to weight it because the right weighting is your threat model, not ours.

Scores are re-read when firmware ships, when a certification lapses, and when a disclosed attack changes what a property is worth. Corrections, teardown data and wallet suggestions are welcome at hossein@walletblueprint.com.
